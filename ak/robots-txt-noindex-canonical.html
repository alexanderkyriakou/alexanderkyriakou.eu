Robots.txt, Noindex, and Canonical: Three different jobs

A gatekeeper, an absolutist, and a proposer walk into a pub. What do they have to say?

The three jobs in a shot

Mechanism Its job Where it goes wrong
Crawling: robots.txt A matching Disallow stops the fetch. A blocked URL can still be indexed without its content, and nothing on the page (noindex, canonical) can be read, because the response is never fetched.
Indexing: noindex A robots meta tag or an X-Robots-Tag header tells Google to exclude a URL once it processes the response. It only works after a successful fetch. An index in the HTML won't cancel a noindex added at the edge.
Canonicalisation: rel="canonical" A canonical names your preferred URL among duplicates. Google groups similar pages and selects a representative, taking your declaration and other signals into account. It is a hint, not a directive. Pointing it at a blocked, excluded or missing page weakens it, and a blocked duplicate can't even be read.

Three different jobs. The gatekeeper (robots.txt) decides who gets in. The absolutist (noindex) says “not in my index”, but only after the fetch has happened and the response has been processed. The proposer (canonical) suggests which page should speak for the others, and may be overruled. The distinction sounds straightforward enough. Things get more interesting when we put them together.

One bicycle, eight ways to buy it

Let's use a fictional gravel bike called the AWGravel. A cycling magazine has reviewed it, and the reviewer rode the Forest Green version. Naturally, the review links directly to that colour.

By the time someone reads the review, however, the shop's default colour is Ocean Blue. The visitor lands on the product page and sees a different bicycle from the one they were reading about.

That's not particularly helpful. Ideally, the link should remember the selection. Now let's add another dimension: frame size.

There are two colours and four frame sizes. A customer wants the Forest Green version in 60 cm, of which there's only one left. Ocean Blue is on backorder. The warehouse consequently has eight stock records, each representing a different combination.

The shop could make those selections addressable using URLs like these:

Model             /bikes/awgravel
Reviewed colour   /bikes/awgravel?colour=forest-green
Selected bike     /bikes/awgravel?colour=forest-green&size=60

With two colours and four sizes, we have eight possible combinations. Counting the model page and the two colour-only selections, that URL pattern produces eleven addressable URLs. That's a good reason to let someone share an exact selection. Whether the shop needs eleven landing pages in organic search is a separate decision.

Open the last URL in a fresh session. The photo, price, stock and add-to-cart SKU should all match the Forest Green bike in 60 cm, even if the visitor has never touched a colour swatch.

Google's product variant guidance describes what preselection should deliver. Merchant Center's landing-page requirements also make that preselection part of the shopping experience.

An organic canonical pointing to the model page can coexist with that deep link because the shopper still receives the requested page. A redirect to the model that drops the selection would change the buying experience.

Keep that distinction in mind. A URL can be perfectly useful to a visitor without necessarily deserving to be indexed as an independent search result.

Crawl access comes before the response

Suppose the shop decides that it doesn't want all eight size and colour combinations appearing in Google. Someone adds a noindex to the product template for those selections.

That sounds reasonable. But another developer decides to tidy up the robots.txt file and adds a rule matching the same URLs.

Now we have two instructions contradicting each other. The browser can still open the selected bike URL and show the noindex meta tag in its source. Googlebot, however, consults the robots rules and skips the request.

Both sides have done exactly what they were told. The problem is that Googlebot cannot read an indexing instruction in a response it never fetches.

Blocked is not the same as unindexed

A Disallow rule stops the fetch, not the indexing. If other pages link to a blocked URL, Google can still index the bare address. Because it never reads the page, the result typically shows little more than the URL. That is why robots.txt is the wrong tool for removing a page from search, as Google's guidance on blocking indexing points out.

In the awgravel shop, the magazine's link to the Forest Green selection is enough to put that URL in front of Google. Blocking it in robots.txt doesn't make it disappear. It only guarantees that Google can't see what the page says about itself.

Blocked pages can't nominate a canonical either

The same mechanism defeats canonicals, and this is probably the most common way the three tools collide. Suppose every selection URL carries a canonical pointing to /bikes/awgravel, and someone later adds this to robots.txt to “save crawl budget”:

User-agent: *
Disallow: /bikes/*?size=

Googlebot no longer fetches the size URLs, so it never reads their canonical declarations. The declaration still sits in the HTML, and every audit tool that looks at the source will report it as present. Google can't use it, and the blocked URLs remain candidates for the index.

If duplicates should consolidate, they have to stay crawlable so that Google can read the canonical.

There is no noindex in robots.txt

One more trap is worth knowing. Google stopped supporting noindex rules inside robots.txt in 2019, so a line such as Noindex: /bikes/ is ignored. Exclusion belongs in the page response, as a robots meta tag or an X-Robots-Tag header, on a URL that Googlebot is allowed to fetch.

Matching, discovery and what to do instead

A crawler can learn a URL from the magazine's link, an internal link or a sitemap before fetching its content. For a particular crawler, check the rule against the actual scheme, host and port, as well as the actual path and query string. A shop on www and a PDF hosted on a separate asset hostname can have different robots files.

My robots.txt checker and multi-crawler rule tester takes you through matching and crawler identity. An "allowed" result answers the rule question. You still need the public response to find out whether the URL serves a product, redirects, or returns an error.

If exclusion is the aim, let Googlebot fetch the URL and serve noindex consistently. Keep it crawlable so the engine can continue to observe that policy.

For a product permanently removed without a replacement, expose its real 404 or 410 instead. Blocking the retired path can hide the status just as effectively as it hides a meta tag.

For a private catalogue, use authentication. Anyone with the address can request a publicly accessible page carrying noindex. An indexing directive isn't access control.

Robots meta tags and X-Robots-Tag

Now, let's move from crawl access to what happens once a crawler retrieves a page.

The headers arrive before the HTML body. That delivery order doesn't give an HTTP header higher authority. Google considers the rules applicable to its crawler, combines compatible restrictions, and uses the more restrictive rule where they conflict.

Here's what that means in a response that looks perfectly fine in a browser.

HTTP/2 200
Content-Type: text/html; charset=utf-8
X-Robots-Tag: noindex

And here's the initial HTML returned for the same URL:

<meta name="robots" content="index, follow">
<link rel="canonical" href="https://bikes.example/bikes/awgravel">

Google applies the more restrictive robots rule here, so the header's noindex excludes the page once Google processes it.

Changing the HTML to index, follow again won't repair the page. Check the CDN, origin and application for the layer adding the header. The self-canonical doesn't make this response eligible for search either.

Scope matters before precedence. Take a generic X-Robots-Tag: noindex and an HTML googlebot tag that says index. Both apply to Googlebot, so the generic exclusion still stands.

Reverse the targeting and a generic max-image-preview:large can coexist with X-Robots-Tag: googlebot: noindex. The crawler name in that header limits the exclusion to Googlebot. Check each relevant engine's support before assuming it interprets another crawler's name or directives the same way.

PDFs give the header a job the HTML can't do

Suppose the AWGravel geometry chart lives at /manuals/awgravel-2026.pdf. The shop wants people to download the chart but doesn't want the PDF appearing in Google Search.

There's no HTML head in a PDF where we can put a robots meta tag. This is where the HTTP header comes in. Send X-Robots-Tag: noindex on the PDF response.

If an HTML manual carries the same chart and the shop wants to consolidate the two formats, the PDF can name its canonical in an HTTP header:

Link: <https://bikes.example/manuals/awgravel-2026>; rel="canonical"

Check that the HTML manual contains the chart. A sales page with a photo and a “download geometry” button is a poor substitute for a table of reach, stack and standover height.

Initial HTML and rendered HTML can disagree

There's another detail worth keeping in mind. What you see in the browser's final DOM isn't necessarily what the crawler received initially.

If the initial response says noindex and JavaScript removes it after stock data loads, Google may skip rendering once it sees the initial rule.

Inspecting the final DOM in your browser can make this look fixed. For a product intended for search, emit the intended policy in the initial response and keep it consistent through rendering.

How Google selects a canonical URL

A canonical doesn't control whether a page can be crawled or indexed. It's a hint with a different job: telling search engines which URL we'd prefer to represent a group of duplicate or near-duplicate pages.

Google compares the main content of pages, groups duplicates or near-duplicates, and selects a representative for each group. The site can declare a preference even if Google ultimately selects another URL.

The first question in an audit is whether the pages belong together at all. A 60 cm preselection on the same bike is a plausible duplicate. Two generations with different frame geometry answer different questions.

Google does not simply take the canonical URL at face value. It considers it alongside other signals to decide which URL should represent a group of duplicate or similar pages. This is also why the canonical you declare and the URL Google ultimately selects are not always the same.

Google has explained this process in some detail and outside of its docs.

Some of the signals Google can consider when deciding which URL should represent a group of similar pages.

Signal What I'd look for on the shop
Permanent redirect A 301 or 308 from a retired product address to its equivalent gives Google a strong signal for the destination. A customer also lands there. Use it when the source no longer needs to serve its own page.
Canonical link A strong preference expressed in the HTML head or an HTTP Link header. Check the final public response. A CMS and a CDN can each emit a different target. Point duplicates directly to the intended representative and give that page a self-canonical.
XML sitemap Google describes inclusion as a weak signal. A sitemap listing the base model expresses a clear preference. Listing the base and all eight buying states adds very little clarity. Leaving a URL out still allows discovery through links.
Internal links Inspect the actual href on category listings, breadcrumbs and copy-links. If every listing opens the default colour parameter, one template quietly makes the variant the most linked version across the website. A swatch taking someone to a particular colour serves a different purpose.
External links The magazine may link to the Forest Green selection. Google has discussed internal and external links among the signals it considers, and link signals to duplicate URLs can consolidate once a representative is selected. Google publishes no backlink count that settles a conflict. One good review is hardly a reason to break a working deep link.

Google documents redirects and canonical annotations as strong signals and sitemap inclusion as weak. Consistent signals can reinforce one another.

It also generally prefers HTTPS and considers membership in relevant hreflang clusters. None of that gives us a numerical formula for predicting a winner.

For the awgravel, this means the shop can keep the green URL working for people following the magazine review, while Google may choose the model page as the representative in search. Those two outcomes aren't mutually exclusive.

Colours, frame sizes and model years

The canonical decision isn't necessarily the same for every type of product variation. Colours, sizes and model years can represent quite different things, even when they're all managed by the same product catalogue.

Colour variations

For a single product page with optional selectors, I'd canonicalise to the stable model URL.

In this shop, that's /bikes/awgravel. The default can change from Forest Green to Ocean Blue next spring while the model URL still means the same thing.

Make each useful selection directly addressable and include the model URL in the organic sitemap. The link in Merchant Center for the green 60 cm bike should still open that exact offer.

A shop can instead maintain distinct colour landing pages, say /bikes/awgravel/forest-green and /bikes/awgravel/ocean-blue.

I'd consider self-canonicals when the shop actually supports those pages as independent destinations, with useful photography, accurate colour-specific offers and stable links. Google recognises a multi-page variant design where the pages have equal standing.

Merely turning a query parameter into a pretty path changes nothing about what the shopper finds there. A different paint swatch on otherwise identical pages may still leave Google choosing one representative.

Frame sizes

Frame sizes usually belong under whichever model or colour page represents them.

Keep the 60 cm URL shareable, with its own availability. A distinct SKU is good inventory management. For an independent search landing page, I'd want a reason someone would seek out that build, such as a smaller-frame version with different wheels and handling, backed by geometry and component information the main page doesn't cover.

Having a separate stock record for every size doesn't automatically mean every size needs an independent search landing page.

Model years

Model years are a product identity decision.

Keep the same URL while it can still accurately answer what buyers and people following older reviews came for.

Say the 2026 AWGravel takes 45 mm tyres and its redesigned 2027 frame clears 50 mm. Silently rewriting the old specification puts the wrong answer in front of someone choosing tyres for the bike in their shed.

Separate generation pages earn their place here. A stable model-family page can link to both where it has a job of its own.

Out of stock and discontinued products

Temporary stock loss calls for an availability update on the affected size or colour. A discontinued bike can still justify a useful, indexable 200 archive with geometry, manuals, compatible parts and a link to the successor.

If the page has an equivalent elsewhere, permanently redirect to it. If it's gone and has no replacement, return 404 or 410.

Google can treat an irrelevant redirect as a soft 404. Send every retired bike to the category and someone looking for tyre clearance lands on a grid of fifty bikes.

The important distinction is between a product that's temporarily unavailable, one that's been discontinued but still has useful information, and one that's certainly gone with no equivalent replacement.

Canonical conflicts, loops and chains

So far, we've looked at fairly straightforward implementations. In practice, different templates, plugins, CMS configurations and edge rules can produce conflicting instructions.

In the examples below, A → B means A declares B as canonical. You can request A, get a 200 and buy the bicycle there. A canonical link doesn't send the browser to B. That distinction matters particularly in a loop, where both pages may load just fine.

Noindex on the source or the target

Suppose A carries both noindex and a canonical to B. Once Google fetches A and processes the exclusion, A is no longer eligible to appear in the index. B does not acquire A's noindex through the link.

Whether A's signals consolidate into B under this combination is a different question, and John Mueller expressed uncertainty about signal transfer when asked about this combination.

Don't combine the two on the same URL. A canonical says "treat this as a duplicate and consolidate it". A noindex says "keep this out of the index". Those are different jobs, so give each URL one of them:

  • If A should consolidate into B, keep the canonical, remove the noindex from A, and keep A crawlable so Google can read the preference. Google's guidance is to use a canonical for consolidation.
  • If A has to be excluded, serve a consistent, observable noindex and drop the canonical to B. A self-canonical on a deliberately excluded A won't restore its search eligibility either.

Now move the noindex to B. A is nominating a page you've asked Google to exclude.

Google can process the exclusion on B once it fetches B. The declaration tells us little about whether Google will select A, find another eligible representative, or surface neither.

If B is the intended landing page, fix B's response. Editing A's HTML alone leaves the exclusion in place.

Two pages nominating each other

Imagine the model page points to the Forest Green variant, while the Forest Green variant points back to the model.

A and B can both return valid product pages while giving contradictory preferences. If Google considers them duplicates, it can use other signals to select a representative. If the main content differs enough, they may never end up in the same cluster.

There's no documented “first page crawled wins” rule. I'd check the indexed URL Inspection result for both, then fix the template that disagrees with the catalogue strategy.

In this example, if A should represent both, have A point to itself, keep B pointing to A, and update category listing meant to link to the model. The review can keep its Forest Green destination.

A chain ending in noindex

Imagine the size selector nominates the colour URL, the colour template nominates the model, and an old edge rule puts noindex on the model.

The chain doesn't transmit C's exclusion back to A and B. Nor does it promise that B becomes the fallback. Canonical consumers can use their own heuristics when declarations are improper.

If C should represent all three, remove C's exclusion, point both duplicates directly to C, and give C a self-canonical. If C should be out if Index, choose an eligible representative for the pages that are equivalent.

A live product pointing to a 404

The Forest Green page returns 200. Its canonical points to the model URL, which returns 404.

The error belongs to the model URL. Once Google processes it, that URL is ineligible and an already-indexed copy is removed over time. The Forest Green page can still be indexed.

The canonical standard explicitly allows consumers to ignore an invalid declaration pointing at a 4xx. Google may select the colour page or another duplicate, and the colour page can also remain unindexed.

Restore the model as an indexable product page if it was accidentally deleted. If the model page was intentionally retired and Forest Green now deserves its own landing page, self-canonicalise that page and update the catalogue links and sitemap.

An audit that only checks whether each source contains a canonical will pass all eight variants while missing the same broken target eight times.

Serving robots directives at the Cloudflare edge

So far, most of the examples have involved instructions in the page itself or in its HTTP response. But where those instructions are added matters too. Sometimes the CMS isn't responsible at all.

Two lines in a production build

On Cloudflare Pages, a plain-text _headers file in the static build output can apply rules to responses on the public hostname.

Suppose the shop adds the following to keep a preview out of search, then ships the same file to production:

/*
  X-Robots-Tag: noindex

That path pattern has no hostname restriction. On a fully static shop, it can put an exclusion on the homepage, every product, and the geometry PDFs.

The pages still render, customers can still order their bikes, and a source inspection can still show a lovely self-canonical. The exclusion travels in the HTTP headers.

As soon as production serves that build, the header is there. How quickly the pages disappear from Search depends on when Googlebot next visits each URL, which could be a different day for the homepage and the geometry chart.

Pages already sets X-Robots-Tag: noindex on its standard preview deployments. If you operate a separate staging hostname, scope a custom rule to that host, for example:

https://staging.bikes.example/*
  X-Robots-Tag: noindex

A header is not protection, though. A staging site that anyone can open is still public, and a crawler that ignores the header, or a leaked link, still reaches it. Put staging behind authentication, for example with Cloudflare Access, and treat the noindex header as a backstop rather than the control.

Replace the broad rule. Adding a narrow index rule beneath it can leave both values in the response because Pages joins repeated matching header values. Google still has an applicable noindex.

On a hybrid site, check one static category and one dynamically generated product. Pages Functions and responses generated by Worker code don't automatically inherit static asset _headers rules. Testing only the dynamic product can make an affected catalogue look healthy.

A response header for a specific set of files

For a shop that wants its downloadable dealer sheets excluded, a Cloudflare Response Header Transform Rule can match the production hostname and a dedicated directory.

For example, use the expression below, then choose Set static for the header X-Robots-Tag with the value noindex. Set replaces existing values of that header at this step, so first check whether those responses carry another restriction you intend to keep.

(http.host eq "bikes.example" and
starts_with(http.request.uri.path, "/downloads/dealer-sheets/"))

Fetch one dealer PDF and the public manual at /manuals/awgravel-2026.pdf. Only the dealer sheet should acquire the exclusion from this rule.

A header rule also covers PDFs and other non-HTML files, which a markup change can't. If the HTML itself needs a robots meta tag, put it in the template at the origin rather than rewriting pages at the edge.

If those files are confidential, enforce access control as well. A search exclusion leaves the download publicly accessible.

If an active transform rule adds the header, fix that rule too. Purging an asset won't remove an active rule that adds a header to each response.

AI crawlers, search indexes and direct visits

Search engines aren't the only ones fetching and processing pages anymore. AI assistants introduce another layer, and it's tempting to assume that the same rules apply everywhere.

Does an AI agent respect noindex or use the declared canonical? First establish which product supplied the result and how it obtained the URL. An assistant searching an index, an automated training crawler, and a user asking an assistant to read a particular bike review involve different operations.

Here's what the providers document. Where a row says a vendor leaves something open, read that as unknown, not as honoured.

Product or path What a publisher can infer
Google AI Overviews and AI Mode To appear as a supporting link, a page must be indexed and eligible for a Google Search snippet. A processed noindex therefore removes that eligibility. Search canonicalisation can affect the representative available from the index.
Claude web search Anthropic describes the robots meta tag noindex as a way to exclude content from the results its search partners supply, and notes that the page can still be visited directly through a link. The same page has a separate section on disallowing Anthropic's own bots, which is a different control from the search-partner route. It leaves header equivalence and canonical selection unspecified.
ChatGPT search and user-requested visits OpenAI documents separate crawlers for these jobs. It uses OAI-SearchBot for search, GPTBot for potential training use, and ChatGPT-User for certain user actions. It says robots.txt rules may not apply to user-initiated visits. The crawler reference gives no general promise that every retrieval path honours a page-level noindex or cites the declared canonical.
Mistral search and Vibe Mistral's crawler documentation identifies MistralAI-Index for search indexing, MistralAI-User for user-requested visits in Vibe, and MistralAI-Training for training data. It explains how to target those roles in robots.txt. It leaves open how Mistral handles a robots meta noindex, an X-Robots-Tag header, or a canonical when choosing a citation.

The distinction becomes more important when an AI answer cites a product URL that differs from the canonical you declared. The URL may have come from a search index, a page fetched in response to a user's request, or a merchant feed. Those routes don't necessarily follow the same rules. I've looked at how AI search products handle robots.txt, noindex, and canonical URLs, including how to investigate which source may have supplied a particular product URL.

Suppose a user supplies the Forest Green URL and the answer cites the model page. Did the assistant read the canonical? Possibly. A search partner may have supplied the model, or the assistant may have followed a prominent model link. The citation alone can't distinguish those paths.

Likewise, seeing a fetch in a log establishes a request, not training use or indexing. The distinction between a crawler requesting a page and a product actually using its content is important.

I go into the individual AI crawlers and their robots.txt controls in more detail, including what a log entry can tell you about the request.

What the public response can tell you

We've covered crawl restrictions, indexing directives, canonical selection, product variations, conflicting signals, edge rules and AI retrieval. The remaining question is how to verify what is actually happening on a live site.

Start in your browser. Open the exact URL you want to investigate, including any query parameters used to select a product variation. Then open DevTools and inspect the document request in the Network panel. Check its status code and response headers, particularly any X-Robots-Tag or Link headers. The Response tab shows the HTML returned by the server, while the Elements panel shows the DOM after the browser has processed the page and run its JavaScript.

These are not necessarily identical. A canonical or robots directive might be present in the initial HTML, added or changed by JavaScript, or delivered through an HTTP response header. Checking both the response and the rendered DOM helps you identify where a directive comes from and whether client-side code changes it.

If you need to inspect the raw response outside the browser, or repeat the same request for comparison, curl is a useful secondary option. For example:

curl -sS -D variant.headers -o save.html \ 'https://bikes.example/bikes/awgravel?colour=forest-green&size=60'

Keep one limit in mind. A plain curl request announces itself as curl, and a CDN, bot-management rule or application can answer it differently from the way it answers Googlebot. You can repeat the request with a Googlebot user agent to look for differences:

curl -sS -D googlebot.headers -o googlebot.html \ -A 'Mozilla/5.0 (compatible; Googlebot/2.1; +http://www.google.com/bot.html)' \ 'https://bikes.example/bikes/awgravel?colour=forest-green&size=60'

A spoofed user agent comes from the wrong network, so bot protection may treat it differently from the real crawler, and a matching result proves less than it seems to. Treat these requests as a way to spot differences. For what Google actually receives, rely on the Search Console live test and verified Googlebot entries in your access logs.

  1. Read the status and every relevant header. Inspect Location, all X-Robots-Tag fields, and any Link headers. For a redirect, fetch the next hop and keep its response separate. Following only the final response can hide the URL where a redirect was introduced.
  2. Read the initial head, then fetch the canonical target. Compare the HTML canonical with the HTTP declaration and resolve the target URL. Fetch the target's status, headers, HTML and own canonical. This is how you catch a valid-looking declaration pointing to a 404, another hop, or a model page excluded at the edge.
  3. Test crawl permission and rendering independently. Check the actual user agent and URL against robots.txt (and verify the crawler actually received the current robots.txt rather than a cached copy or server error). If JavaScript changes the metadata, compare the initial HTML with the rendered document. On Cloudflare, sample the production hostname, a preview, and both a matching and a neighbouring path.
  4. Put dates beside the evidence. Access logs can show a verified Googlebot fetch after the deployment. Search Console's live test helps check current accessibility. The indexed URL Inspection report shows the last recorded crawl and Google-selected canonical where available. A live test can't predict the canonical Google will select.

For the AWGravel, I'd want the magazine's link to keep opening the Forest Green version even if Google shows the model page in search. The reviewer chose that colour, and someone following the review has a good reason to land there.

A rider coming back two years later to check whether a 50 mm tyre fits has an equally good reason to find the 2026 geometry chart, right down to the year in the URL.

That's where I'd start with a real catalogue. Which details would someone reasonably expect this address to remember? For the reviewed bike, it's the colour. For its owner, it's the frame they bought.

Once that's clear, it's much easier to decide which URLs belong together in search and which ones deserve a page of their own.

And perhaps that's a good point to finish our beer. The gatekeeper, the absolutist and the proposer can go back to arguing about something else.
